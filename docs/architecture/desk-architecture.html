Trade Desk · architecture from a clean sheet

If the desk were built from the beginning

The same three jobs — find stocks, test strategies, journal trades — and the same research rules, rebuilt around what two weeks of review found on the real box. Every design choice below points at the failure it prevents.

Grounded in: the 2026-10 review (D-S*, F-*, S-*), the live box (913 MB RAM, pm2), and the repository at main.

The principles

Tools are data, not programs

A tool is a row: its screeners, windows and capture times. One engine runs all of them. Adding a tool costs a few kilobytes.

Today: 90 MB per tool, 6 stopped because the box is full.

One writer for every fact

Every shared table names its single owner. Others read. A fact with two sources stores both, with a stated priority.

Prevents F-21 and the lost updates of nine processes writing one file.

One front door

Everything under one HTTPS address, routed by path. One login. No other port open to the internet.

Today: 13 ports, cross-port cookie and CORS workarounds.

One clock

One scheduler owns every timed job, with a run history and an alert when a run fails or does not happen.

Today: 60+ cron jobs across 5 processes, plus pm2 cron and systemd.

Config is checked when saved

A capture before its screener's window, a window outside market hours, a tool with no screener: refused with the reason.

Prevents D-S9.

Isolate results, share facts

Each tool's candidates, registers, shortlist and model stay strictly its own. A price or a news story about a ticker is fetched once and used by all.

Keeps the research rule; removes duplicated fetching.

As of the date, always

Every stored number carries when it became known, so a backtest can never read the future. qp already works this way; it becomes the rule everywhere.

F-20, F-26, F-28 were all look-ahead.

Proven before it ships

Every pull request runs the full test suites automatically. A red check blocks the merge.

Today: no CI.

Front door new

  • HTTPS certificate, automatically renewed
  • The one login (today's code, moved to the edge)
  • Routes /chart to quant, everything else to desk-web
  • Closes ports 3000–3120 and 8765

desk-web reshaped

  • One shell, one top bar, every page
  • All tools behind /api/tools/T2/…
  • Journal as a module, same login
  • Never runs a timed job — it only answers

desk-worker new

  • The only scheduler: discovery scans, R1–R4 captures, outcome, training, broker fetches, backups
  • Each run recorded: started, finished, rows, error
  • A missed or failed run pushes an alert

quant kept

  • Today's qp: indicators, strategies, backtests, O'Neil
  • Reads registers from the database, not 11 ports
  • Sole writer of market model, groups, SIC map

Why Postgres instead of today's SQLite files: three programs write at once, and one database gives one backup, one place to query, and transactions across tools. On the current box it costs about 60–100 MB, less than one tool process does today. If the desk stays on one machine, SQLite in WAL mode with a single writer per file is the lighter alternative; the ownership rules above matter more than the engine.

Getting there without a rewrite

Each step ships on its own, keeps the desk working, and is reversible. The order puts safety and cheap wins first and the largest change last, when everything around it is already proven.

  1. CI on every pull requestGitHub Actions runs Jest and qp's run_all; a red check blocks merging.risk: none · about a day
  2. One front doorCloudflare Tunnel (you already use Cloudflare) gives HTTPS on one address; close every port in the EC2 firewall. Today's login moves in front.needs: a domain on Cloudflare · risk: low
  3. Config checked on saveCapture vs window, windows vs market hours, mirrors vs bases. Fixes D-S9 and its whole class.risk: low
  4. One writer per shared factThe data/*.json files become tables with a named owner, starting with the industry map, market model and groups.risk: low–medium
  5. One scheduler with a run history and alertsdesk-worker takes the timed jobs from every tool, pm2 cron and systemd. A failed backup or scan reaches your phone.risk: medium · run old and new side by side for a week
  6. Tools as configurationOne engine hosts every tool. Migrated one tool at a time; for a week each tool runs in both, and its R1 registers are compared row by row before the old process is stopped.risk: the largest step · fully reversible per tool
  7. Postgres and the Parquet lakeThe per-tool SQLite files load into one database; daily registers land in R2 as Parquet for analysis. Required for Railway, optional on EC2.risk: medium · the backup proves the copy
  8. One web shellThe three apps' pages share one bar, one stylesheet, one login, same origin — the cross-port code is deleted.risk: low · cosmetic to you

What stays exactly as it is

  • The research method: one photo a day per tool, entries A and B, outcomes in ATR, the benchmark (Stocks in Play).
  • Each tool's results, model and history isolated from every other tool.
  • "A label, never a filter" for every shared fact on a card.
  • qp's engine, its as-of discipline and every strategy you have saved.
  • Archived tools stay readable forever.
  • The nightly backup to Cloudflare R2 and the one password.

Decisions that are yours

  • Where it runs. Stay on EC2 (cheapest, already working) or move to Railway (managed Postgres and deploys, but a monthly bill that grows with usage). The design works on both; steps 1–6 are the same.
  • A domain name for the one HTTPS address — needed for step 2.
  • How far to go. Steps 1–5 remove most of the risk found in the review for a few days of work. Step 6 is where the memory and per-tool cost go away.
